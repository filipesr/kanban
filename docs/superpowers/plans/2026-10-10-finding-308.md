# The cause of #308 — the review notification does not fire on a normal completion

**In one sentence:** the notification is only emitted for a `reviewReason` in
`hook | attention | error`, and a task that **finishes successfully** gets
`reviewReason: "exit"` — which is not on the list. So it announces when the agent fails and
stays silent when it succeeds.

## The two lines

Where the reason is assigned — `src/terminal/session-state-machine.ts:59`:

```ts
let reason: RuntimeTaskSessionReviewReason = event.exitCode === 0 ? "exit" : "error";
if (event.interrupted) { reason = "interrupted"; }
```

Where the notification is filtered — `src/server/runtime-state-hub.ts:530-532`:

```ts
(summary.reviewReason === "hook" ||
 summary.reviewReason === "attention" ||
 summary.reviewReason === "error")
```

The full enum (`src/core/api-contract.ts:259`) is
`["attention", "exit", "error", "interrupted", "hook"]` plus `null`. **Two reasons are left out
of the filter: `exit` and `interrupted`.**

## Why the issue survived six months

Anyone reproducing with a task that **fails** sees the notification working — the `error` path
is on the list. Only the **success** path is silent, and it is the common one. The report in
#308 describes exactly that: *"wait for search to complete and task to shift to review
section"*.

## The fix, and the question it raises

The obvious fix is to add `exit` to the filter. `interrupted` is a product decision: a task a
human interrupted may not need to tell that human about it. **Proposal:** include `exit`, leave
`interrupted` out, and say so in the PR for the maintainer to decide.

## A second condition, unrelated but worth raising in the PR

`broadcastTaskReadyForReview` (`runtime-state-hub.ts:326-329`) **returns early when there is no
runtime client** for that workspace — so with no tab open there is nothing. That is coherent
for a browser notification, but it is also why no other destination can exist today, and it is
the point the hub design addresses.
